# AgentPlat 1.4.0 — release preparation

Status: candidate preparation; no 1.4.0 package is published by this change.
Registry checks on 2026-10-18 found 1.3.0 for Rooms and Runner; all 68 proposed
1.4.0 package-version endpoints returned 404. Existing 1.3.0 bytes remain intact.

## Scope

The coordinated cohort remains 68 packages. Version 1.4.0 adds the persistent
memory and reviewed-definition capabilities integrated through PR #222:

- Stable-agent subjects and separately authorized personal/shared audiences.
- Immutable corrections, retirement, validity/retention and exact context references.
- An opt-in PostgreSQL memory ledger with its own migration application ID.
- Exact proposal/approval/evaluation coordinates in existing governance history.
- Consistent legacy context/tool retrieval and replay/concurrency controls.

Existing 1.x APIs, authority owners, legacy Room migrations, evidence baselines
and published versions remain unchanged. Memory retention filtering is not physical
erasure, and consumer membership/identity, UI, source services and deployment
remain host responsibilities. See the [consumer guide](../getting-started/persistent-memory-consumer.md).

## Artifact verification

Both protected release workflows now invoke `verify:memory-consumer` in their
full-scope exact-artifact step. `AGENTPLAT_PREPACKED_TARBALL_DIRECTORY` selects
immutable input: the verifier validates the complete release manifest and cohort
using the existing shared release validators, checks the source commit/version/tag,
and copies only the memory consumer's required dependency closure. It does not
build or pack replacement bytes in this mode.

Copied bytes must still match each manifest size and SHA-512. Consumer installs,
frozen pnpm install, npm install and npm ci, public types and the PostgreSQL
cross-conversation fixture run against those exact tarballs. Proof output goes to
`dependency-audit/memory-consumer`, outside the immutable release directory, which
continues to contain only its manifest and 68 archives.

## Gates and publication boundary

- Keep required protected-main CI, adoption, CodeQL, compatibility, production
  audits and all prior release checks.
- Keep historical 1.3.0 release-line fixtures; add a distinct exact 1.4.0 cohort.
- Use the existing version transaction to update root plus all 68 package manifests.
  Regenerate and verify the lockfile; workspace links require no new dependency.
- After this preparation PR passes and integrates, dispatch the protected workflow
  with `scope=all`, `dist_tag=latest`, `dry_run=true` for a fresh commit-bound cohort.
- No publish/staging step, environment approval, registry tag change or enablement
  flag change is performed by this preparation. Publication requires its own
  deliberate workflow dispatch and the existing release approval/identity checks.

A local package consumer proves bounded integration, not production-scale quality
or operational readiness. Only the successful protected preparation and exact
artifact evidence qualify the release candidate for subsequent publication.
